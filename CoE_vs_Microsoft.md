# CoE Starter Kit vs. Native Microsoft Capabilities

Granular feature-by-feature comparison of every component in this fork against its closest
native Microsoft equivalent (Power Platform admin center, Purview, Entra, Viva, or elsewhere),
as of **9 August 2026**. Built from a direct inventory of this codebase (flows, Dataverse
tables, canvas/model-driven apps, pipeline templates), cross-referenced against current
Microsoft Learn docs, release-wave plans, dated blog posts — then re-verified a second pass
against in-repo documentation, the actual flow/entity source for non-obvious configuration and
behavior, and community/MVP-recommended alternatives to both the CoE feature and its native
replacement.

**Purpose**: turn this into a prioritized task list of what to retire, what to keep because
Microsoft has no substitute, what needs its dependency re-pointed before it can be retired, and
what non-Microsoft alternative exists if neither the CoE component nor native coverage is good
enough. See §7 for that task list.

**Caveat**: Power Platform ships monthly. Every "Status/Date" below reflects what was
verifiable via Microsoft Learn/blog sources on 9 Aug 2026 — re-check anything load-bearing
before acting on it, per the standing guidance in `KNOWLEDGE-Claude-Craig.md`.

**Legend**
- **Coverage** — Full: native fully replaces the CoE feature · Partial: native covers part of
  it, or covers it but only as a flag/recommendation rather than an automated workflow · Gap:
  no native equivalent exists.
- **Retire?** — Yes: safe to drop, native covers it · Partial: drop part, keep part (see notes)
  · No: keep, it's a genuine gap · N/A: not a Microsoft-comparable feature (internal plumbing,
  installer, demo/sample).
- **Alternative (non-MS)** — a community/commercial/OSS option to consider instead of either
  the CoE component or the native feature, tiered by source reliability: **T1** = named
  Microsoft MVP/RD blog, official Microsoft OSS project, or official ISV partner docs · **T2**
  = established community site/newsletter, reputable consultancy blog, well-known GitHub repo
  with real adoption, or a vendor's own product docs (no named author) · **T3** = anonymous
  forum/Reddit post, low-traction blog, or an unverified vendor marketing claim. **Barrier** —
  HIGH = free/OSS/self-run (low barrier to entry) · LOW = requires a paid third-party
  license/subscription (real barrier to entry) — note this is barrier-to-entry, so *higher* is
  better/easier to adopt.

**Headline finding from the alternatives pass**: across almost every genuine process gap
(inactivity workflow, quarantine sweep, compliance BPFs, Teams justification nudge, orphaned
reassignment), commercial governance vendors (Rencore, CoreView, Syskit Point) only document
the *detection* half (find inactive/ownerless/non-compliant resources) — none has verifiable
documentation of the *workflow* half (approval chains, manager escalation, grace periods,
adaptive-card delivery) that the CoE kit actually implements. Named MVPs who've written about
these areas (Jukka Niiranen, Amber Weise, Alex Shlega, Lewis Baybutt) consistently describe and
recommend *using the CoE kit's own implementation* rather than proposing a substitute. This
reinforces `KNOWLEDGE-Claude-Craig.md` §2's original conclusion — the market gap really is in
process automation, not visibility — and means most "Alternative" cells below are honestly
"none found," which is itself the finding.

**Dependency risk**: rows marked "Yes" above (app/flow/PVA/solution/Portal inventory sync, Command Center,
audit sync, BYODL) all write into Dataverse tables — `admin_App`, `admin_Flow`, `admin_Maker`,
`admin_PVA`, `admin_Solution`, `admin_CoESolutionMetadata`, `admin_CustomizedEmail`,
`admin_SyncFlowErrors`, `admin_AuditLog` — that are **read by nearly every other solution in this
repo** (Audit Components' compliance/inactivity/quarantine flows, Nurture's Pulse Survey/Training/
Newsletter, ALM's release-history flow, and `business_value_core`'s AI-usage reporting — see §6).
Retiring the sync flows outright would silently break those consumers.

**Known issue independent of any retirement decision**: this fork's own `Documentation/ReducingAzureLogAnalyticsCosts.md`
and `ISSUE_RESPONSE_LOG_ANALYTICS_COSTS.md` document a live, unresolved cost problem in the
**current v4 inventory-sync flows themselves** (not the already-deprecated `AuditLogs` solution)
— the Power Platform for Admins connector requires user-based, not service-principal, auth,
which generates non-interactive sign-in logs billed per-GB in Log Analytics. Retiring
`CenterofExcellenceAuditLogs` (§3) does nothing to fix this; whatever inventory-sync layer
survives §1's pruning still carries this cost, and the doc's own suggested fix (excluding the
CoE service-account UPN via a Log Analytics transformation rule) trades away sign-in visibility
for that account to get it.

## 7. Task list — prioritized

### Retire outright (native fully covers it, low/no dependency risk)
- `CenterofExcellenceAuditLogs` — whole solution, already self-labeled deprecated (does **not** fix the real Log Analytics cost issue living in the current v4 sync flows — track that separately)
- `Theming`'s theme-editor/gallery/starter templates — native Fluent 2 theming supersedes them and old theming is being phased out regardless (keep an eye out for anyone actually using the *runtime* color-picker case before deleting those two PCF controls specifically)
- `CenterofExcellenceALMAccelerator`, `ALMAcceleratorForMakers`, `CenterofExcellencePipelineAccelerator` — Microsoft has already deprecated the lineage; closes the open ADO-template-folder decision. Budget separately for replacing the AzDO-infrastructure-*provisioning* piece (project/service-connection/variable-group creation) — native Pipelines doesn't do that part, `pac` CLI/Build Tools scripting does
- Nurture: Newsletter (known maintenance treadmill — one RSS source already went stale once), Template Catalog, Champion/Maker Directory, `admin_Featureadmin`/`admin_SharedContent` dead tables
- Command Center dashboard/bookmark flows, M365 service-message pull, App Catalog request-access flow
- Teams environment inactivity-cleanup flow specifically (keep the business-justification-request flow — see below)

### Retire, but re-point dependents first (§1/§4/§6 dependency risk)
- CoreComponents' v4 inventory sync (apps/flows/PVA/model apps/solutions/Portals) — before deleting, decide how Pulse Survey, Compliance flows, Training-in-a-Day, orphaned-cleanup, quarantine, **and `business_value_core`'s AI-credit-usage reporting** will get their data instead: keep a thin sync layer for just the columns those consumers need, or rewrite them against the native Inventory API directly. Whatever survives still carries the known Log Analytics cost issue (user-based PPfA connector auth) — fix that regardless of scope
- DLP Editor + its Dataverse sync flows — safe once Advanced Connector Policies is adopted, but confirm no other flow reads `admin_DLPPolicy`/`admin_Connector` for something other than the editor UI first
- Quarantine action itself — confirmed the action was always native underneath (`Set-AppQuarantineState`); re-point cleanly to it if not already effectively equivalent, keep the grace-period sweep logic
- Legacy v3 sync/cleanup flows — redundant with v4 **except `AdminSyncTemplatev3Connectors`**, which is a named critical flow syncing standard (not custom) connectors and should NOT be pruned with the rest

### Keep — genuine gaps, no native substitute, and no credible non-Microsoft alternative either
- Compliance Detail Request + Developer Compliance Center + all 5 Approval BPFs (only adjacent building block found: Microsoft's own generic `powercat-business-approvals-kit`)
- DLP Impact Analysis and, especially, the DLP policy change request approval workflow — a documented real incident (444 flows suspended tenant-wide via exactly this class of automation) argues for keeping a human in the loop here, not just "no native substitute"
- Environment Request (self-service create + approval + provision, including its DLP-request linkage)
- Inactivity notifications workflow and Orphaned resource reassignment — native only *flags*, commercial tools (Rencore/CoreView/Syskit) only document detection, and Syskit explicitly *cannot* reassign a flow's Primary Owner. The orphaned-reassignment flow's manager-escalation-on-404 logic is genuinely more sophisticated than anything else found
- Teams environment business-justification request flow (keep this half even though the inactivity-cleanup half retires) — remember it and orphaned-reassignment both hit a hard ceiling in GCC High/DoD (no Teams adaptive cards), not just a feature gap
- RPA/desktop flow inventory, connection reference identities, BPF inventory, AI Builder model registry
- Innovation Backlog (but stop describing its complexity score as calculated — it isn't, in this fork's shipped source), business value toolkit (note the AI-usage dependency above), admin task analysis planner (genuinely zero-dependency, lowest-risk keep in the whole kit)
- Training in a Day logistics wrapper, Maker Assessment skills quiz, Pulse Survey (fix the hardcoded English-only AI call and the doc's false "translates" claim if kept; not a free swap for Viva Pulse either way)
- The runtime (in-app, end-user-facing) color-picker use case in Theming, if anyone's actually using it

### Reassess later (native is close but not proven yet)
- DLP Impact Analysis — Microsoft's own ACP GA post names real impact analysis as future work; re-check each monthly release
- AI Builder model registry — usage/credits are covered, a model catalog might land later; also re-check the whole row soon given AI Builder Capacity Add-on End-of-Sales and the 1 Nov 2026 seeded-credit removal
- Capacity/Add-on alerts — native Monitor › Alerts genuinely exists now (custom thresholds, up to 5 recipients, Managed Environments only) — narrower than CoE's tenant-wide/any-recipient version but no longer "unverified"

### Not previously inventoried — decide its fate too
- `CenterofExcellenceResources/Release/PowerPlatformHub/` (SharePoint PnP template) — real, load-bearing, Microsoft's own recommended asset that several Nurture flows (and `business_value_core`'s success-story publishing) actually depend on. Low maintenance risk (one-time provisioning script, not a live sync) — keep it, but read the known deployment friction (PowerShell version mismatches, script-signature blocking) before anyone redeploys it

### Known issues worth fixing regardless of any retirement decision
- Log Analytics cost overrun in the current (not deprecated) audit/inventory sync flows — user-based, not service-principal, connector auth
- `admin_EnvironmentSecurityRolePermission` has no built-in cleanup job and can grow to 10+GB — the kit's own docs admit this
- Shipped default env vars and URLs point at Microsoft-internal tenants/mailboxes (Developer Compliance Center URL, inactivity-notification mailboxes) — trivial but must be overridden before any go-live, worth a setup-wizard check if one doesn't already exist
